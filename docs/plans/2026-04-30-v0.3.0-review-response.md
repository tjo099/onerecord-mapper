# v0.3.0 Plan Review Response

**Date**: 2026-04-30
**Reviewers**: Architect (`comprehensive-review:architect-review`), IATA domain expert (`general-purpose`), Skeptical engineer (`general-purpose`) — three parallel reviews.
**Plan reviewed**: `docs/plans/2026-04-30-v0.3.0-implementation.md` (rev 1, 2452 lines)

This document synthesizes the three independent reviews, identifies the critical findings (which I have **independently verified against the canonical IATA-Cargo ontology**), records mechanical fixes already applied, and surfaces the one strategic decision that requires owner input before kickoff.

---

## TL;DR

Three reviews surfaced a much bigger finding than expected: **the v0.2-shipped library has significant spec-name divergence from the canonical IATA OneRecord cargo data model 3.2 ontology** — already shipped, not introduced by v0.3. The v0.3 plan as drafted would have entrenched this further. Verified divergences include enum values, property names, and class restrictions on `Shipment` and `BookingOption*`.

Two paths from here:

- **Path A (spec-compliance pivot)**: v0.3 includes the spec-name corrections as a coordinated breaking change, alongside the security-workflow batch and the deviation closures. Library becomes actually spec-faithful. Effort jumps to ~80-100 PD / 14-16 weeks.
- **Path B (document, defer)**: v0.3 ships as planned (mechanical fixes applied), with a new deviation #13 enumerating every discovered non-spec name. Correction work is deferred to a future spec-fidelity release. Effort stays ~70-90 PD / 12-14 weeks.

Recommendation: **Path A**. It is the right alignment for the "publicly verifiable IATA OneRecord 3.2" positioning — anyone diff'ing the library against the canonical ontology will find the divergences immediately, and the longer they live, the more painful the breaking change becomes.

This document calls out the decision; downstream plan edits are conditional on it.

## 1. Verified critical findings (independently re-checked against the canonical ontology)

I fetched the canonical ontologies (`IATA-1R-DM-Ontology.ttl` at `owl:versionInfo "3.2.1"` and `IATA-1R-CL-Ontology.ttl`) from `IATA-Cargo/ONE-Record` master and grep'd them. The IATA expert findings are accurate.

### 1.1. BookingOptionStatus values are non-spec

**Canonical** (`IATA-1R-DM-Ontology.ttl:5491-5506`):
```turtle
:BookingOptionStatus rdf:type owl:Class ;
                     owl:equivalentClass [ rdf:type owl:Class ;
                                           owl:oneOf ( :BOOKABLE
                                                       :BOOKED
                                                       :EXPIRED
                                                       :NONBOOKABLE
                                                       :NOT_BOOKABLE
                                                       :ON_REQUEST
                                                       :QUEUED
                                                     )
                                         ] .
```

**Library** (`src/codes/enums.ts:47-53`): `REQUEST_PENDING / REQUEST_ACCEPTED / REQUEST_REJECTED / REQUEST_REVOKED`.
**Library** (`src/classes/booking-option/schema.ts` per `spec-deviations.md:267`): `OPTION_PROPOSED / OPTION_ACCEPTED / OPTION_REJECTED`.

Neither matches the canonical 7-value oneOf. This is a v0.2-shipped divergence.

### 1.2. BookingStatus values are non-spec

**Canonical** (`IATA-1R-DM-Ontology.ttl:5730-5742`):
```turtle
:BookingStatus rdf:type owl:Class ;
               owl:equivalentClass [ ... owl:oneOf ( :CONFIRMED :DELETED :QUEUED :REJECTED ) ] .
```

**Library** (`src/codes/enums.ts:39-45`): `REQUEST_PENDING / REQUEST_ACCEPTED / REQUEST_REJECTED / REQUEST_REVOKED`.

Different vocabulary entirely. The plan's Phase 3 bakes `bookingStatus: 'REQUEST_ACCEPTED'` (plan line 1310) — also non-spec.

### 1.3. Property name `optionStatus` is non-spec

**Canonical** (`IATA-1R-DM-Ontology.ttl:2403-2408`):
```turtle
:statusBookingOption rdf:type owl:ObjectProperty ;
                     rdfs:range :BookingOptionStatus ;
                     owl:comment "Domain :BookingOption" .
```

**Library** uses `optionStatus`. Same field, non-spec name. Round-trip JSON-LD against any spec-compliant peer (NE:ONE Server) will fail field-name matching unless NE:ONE Server has been similarly rolled back, which is unlikely.

### 1.4. `Shipment.containedPieces` and `Shipment.pieceCount` are non-spec

**Canonical** (`IATA-1R-DM-Ontology.ttl:735-741`):
```turtle
:containedPieces rdf:type owl:ObjectProperty ;
                 rdfs:range :Piece ;
                 owl:comment "Domain :Piece" .  # ← NOT Shipment
```

`:containedPieces` is for **nested-piece (sub-piece) trees**, not the top-level Shipment→Piece collection. The Shipment→Piece collection in the canonical ontology is `:pieces` (with inverse `:ofShipment`).

`:pieceCount` does not exist as a property in the canonical ontology. The closest match is `:pieceCountForRate` on `WaybillLineItem` (`IATA-1R-DM-Ontology.ttl:4076-4080`). Library's `Shipment.pieceCount` (in `src/classes/shipment/schema.ts:13`) is invented.

The Phase 4 cross-node constraint `Shipment.pieceCount === Shipment.containedPieces.length` (plan Task 4.3) validates a relationship that has no spec basis. The defensible cross-node check is **inverse-property consistency**: if Waybill `W` references Shipment `S` via `:shipment`, then `S.waybill === W.@id`.

### 1.5. `requestStatus` not in the canonical ontology

Grep of both ontologies for `requestStatus` and `RequestStatus` returns **zero matches**. Library uses `BookingRequest.requestStatus` and `BookingOptionRequest.requestStatus` with the `REQUEST_*` enum. Both the property name AND the enum values are inventions.

### 1.6. `Shipment.securityDeclarations` is 3.2.1-only

**Canonical change-log header** (`IATA-1R-DM-Ontology.ttl:88-89`):
```
- Added securityDeclarations to Shipment (#344 & #346)
- Added issuedForShipment to SecurityDeclaration (#344 & #346)
```

Both properties land in the same PR pair, so the version-pin discipline is internally inconsistent in the v1 plan: `Shipment.securityDeclarations` would be added (3.2.1-only) while `SecurityDeclaration.issuedForShipment` is deferred (also 3.2.1).

**Decision**: bump pin to 3.2.1. The 3.2 → 3.2.1 delta is small, coherent (two PRs), and aligned with what NE:ONE Server actually serves. Eliminates the artificial deferral.

### 1.7. `BookingOptionRequest.forBookingRequest` does not exist on the library schema

**Library** (`src/classes/booking-option-request/schema.ts:7-16`) declares only `forBookingOption: safeIri()` and `requestStatus`. There is no `forBookingRequest` link.

**Plan** (line 1362-1364) constructs the carrier-side `Booking` from `req.forBookingRequest` — a field that doesn't exist. This is a real BLOCKER for Phase 3 Task 3.4 as drafted.

### 1.8. `confirmBooking` action is invented

The canonical state model treats acceptance of a `BookingOptionRequest` as the transition that produces a `Booking{bookingStatus: CONFIRMED}`. There is **no separate confirm action** in the canonical state diagram. `BookingStatus` does not include a non-CONFIRMED accepted state from which a confirm action would transition.

Plan Phase 3 Task 3.4 introduces `confirmBooking(b: Booking) → Booking`. This should be **deleted from v0.3 scope**. The acceptance-of-BookingOptionRequest IS the act of producing CONFIRMED Booking.

## 3. Strategic decision: Path A or Path B

This is the **only decision** that genuinely requires owner input before any v0.3 work begins.

### Path A — Spec-compliance pivot (recommended)

**What it changes:**
- v0.3 corrects the 7 verified spec-name divergences as a coordinated breaking change.
- Property renames: `optionStatus` → `statusBookingOption`, `pieceCount` removed (computed from `pieces.length`), `containedPieces` removed from Shipment (becomes `pieces` via the canonical inverse), `requestStatus` either removed or its enum aligned to whatever the canonical state-machine document declares (per API spec 2.2.0 §5.4 verification).
- Enum values match canonical: `BookingOptionStatus = BOOKABLE/BOOKED/EXPIRED/NONBOOKABLE/NOT_BOOKABLE/ON_REQUEST/QUEUED`; `BookingStatus = CONFIRMED/DELETED/QUEUED/REJECTED`.
- Spec pin bumped to 3.2.1; both `Shipment.securityDeclarations` and `SecurityDeclaration.issuedForShipment` ship.
- `confirmBooking` deleted from scope; the act of confirming IS `acceptBookingOptionRequest`.
- Phase 3 (booking-flow rework) becomes substantially larger — multi-property + multi-enum + STATE_DIAGRAM rewrite + every test fixture + every snapshot.
- All 33 snapshot baselines regenerate.
- Public API surface change is a major SemVer signal; in 0.x territory this is fine but the CHANGELOG needs a clear `BREAKING CHANGES` block.

**Effort**: ~80-100 PD / 14-16 weeks.

**Justification**: the library's positioning is "publicly verifiable IATA OneRecord 3.2 + API 2.2.0" (`README.md:1-3`). Anyone running the test suite against the canonical ontology — which is what "verifiable" implies — will find the divergences. Shipping v0.3 with the divergences intact undermines the marquee claim. Path A makes the claim defensible.

**Risk**: 14-16 weeks is a long stretch with no public signal. Mitigation: consider releasing v0.3 in two minor versions — `0.3.0` ships the spec-name corrections only; `0.3.5` ships the security-workflow batch + deviation closures. Two clean releases.

### Path B — Document divergence, defer correction

**What it changes:**
- v0.3 plan as drafted (with mechanical fixes applied) ships.
- New deviation `#13` documents all 7 verified spec-name divergences as known issues, deferred to a future spec-fidelity release (could be `v1.0.0`).
- README "publicly verifiable" claim is tightened to acknowledge the divergence: "verifiable round-trip semantics + test infrastructure; spec-name fidelity work is tracked in deviation #13 and pending v1.0."
- `confirmBooking` still deleted from scope (independent finding).
- Spec pin bump to 3.2.1 still recommended (independent finding).

**Effort**: ~70-90 PD / 12-14 weeks (the Phase 4/7/8 work + the security batch + the v1 plan's deviation closures).

**Justification**: keeps momentum, ships value sooner, avoids a 14-16 week dark window. Acceptable if the maintainer acknowledges the "verifiable" claim is partial until v1.

**Risk**: every integration that consumes the library produces wire payloads with non-spec field names, propagating divergence into integrator codebases. Two years from now those integrators are upset when v1.0 breaks every field they wrote.

### My recommendation

**Path A** is the right thing for an OSS project that markets itself on spec fidelity. The honest version of "demand-driven OSS implementation" doesn't include silently-wrong field names.

If shipping speed matters more than spec fidelity: Path B is honest as long as the "publicly verifiable" framing is downgraded to match.

**This decision blocks Phase 3 in either case.** Make it before kickoff.
