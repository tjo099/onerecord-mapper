# v0.6.0 Quote & Book Charge Chain Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship `@flaks/onerecord` 0.6.0. It adds the ONE Record 3.2 `Price`,
`Ratings` and `TransportLegs` classes, nine embedded shapes, and complete
ontology property sets on `BookingOption`, `BookingRequest` and `Booking`,
while every payload that 0.5.0 accepted keeps parsing. A vendored-ontology
guard checks all of it.

**Architecture:** This release adds Zod schemas inside the existing
per-class codec architecture:

- one directory per LogisticsObject class, under `src/classes/<kebab>/`;
- internal embedded shapes in `src/classes/shared/distribution.ts`;
- every class registered in the `CLASSES` map, from which the facade,
  mapper and `CODECS` derive.

Correctness rests on three tests:

- a guard test that diffs the schemas against IATA's own TTL files;
- a property test that uses the published 0.5.0 package as its oracle;
- an integration test over the whole chain.

**Tech Stack:** TypeScript 5.6 (`strict`, `exactOptionalPropertyTypes`,
`noUncheckedIndexedAccess`), Zod 4, Vitest 4, fast-check 3, Biome 1.9, bun 1.3.

**Spec:** `docs/specs/2026-11-13-v0.6.0-spec.md` (r3) is normative. Read it
alongside this plan. Every schema's exact field list and Zod encoding is in
spec §2–§5, and tasks cite the section rather than repeating it. The design
is in `docs/specs/2026-11-13-v0.6.0-design.md`; review history is in
`docs/plans/2026-11-13-v0.6.0-spec-review-response.md`.

## Global Constraints

- The ontology pin stays 3.2.0, so `CARGO_ONTOLOGY_VERSION` stays unchanged
  at `'3.2.0'`. Line citations (`Lnnnn`) refer to the official
  `2025-07-standard` file at IATA commit
  `49e8ac1bfdc24d76fddf307e87f36e381b6941b1`.
- Wire profile:
  - references are bare IRI strings, via `safeIri()`;
  - codes are bare tokens;
  - `xsd:dateTime` values carry a timezone, via `z.string().datetime({ offset: true })`.
- Every object schema is `.strict()`. Arrays are `z.array(...).optional()`;
  an empty `[]` is rejected after parsing as `cardinality_violation`
  (existing `findFirstEmptyArray`).
- No new runtime dependency. One new devDependency:
  `onerecord-0-5-0` = `npm:@flaks/onerecord@0.5.0`.
- No new `ParseError` kind. `test/unit/api-surface/parse-error-kinds-locked.test.ts`
  stays untouched.
- Existing `test/snapshots/classes/booking*.snapshot.json` files must stay
  byte-identical.
- In the three chain classes, existing keys keep their 0.5.0 relative order,
  and new keys are appended after them.
- New classes' `serialize` throws `SerializationError` with the message
  `SerializationError[invalid_application_object]: serializeX: invalid input`.
  Copy `src/classes/co2-emissions/serialize.ts`.
- `bun run test` alone is NOT a green signal. Every task ends with
  `bun run typecheck && bun run lint && bun run test`.
- Commit messages end with the trailer
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- Never tag, push or publish. That needs the owner's approval after Task 14.

## Review Focus

These five input classes are the ones most likely to bite real users, and
the spec does not pin them. Each is pinned by a test in the task named.

1. **Mixed fleet.** A legacy-shaped object (0.5.0 shape) serialized by 0.6.0
   must still be accepted by a 0.5.0 receiver, since Skidd and Booking Portal
   stay on 0.5.0. Expected: 0.6.0 serialize adds no keys, and `S05` accepts
   the output. Pinned in Task 8.
2. **Single value for a multi-valued property.** JSON-LD peers often send a
   scalar where the ontology allows many, for example
   `Booking.additionalInformation: "text"`. Expected: `zod_validation`. The
   package profile requires arrays, and the behaviour is documented, not
   silent. Pinned in Task 5, and noted in deviation #22's profile text in
   Task 14.
3. **Datetime timezone variants on `offerValidTo` and `TransportLegs.departureDate`.**
   Expected: `...Z` and `...+02:00` are accepted; a value without a timezone
   is rejected with `zod_validation`. Pinned in Tasks 4 and 7.
4. **Negative amounts** (credit lines) in `Ratings.subTotal`,
   `Price.grandTotal` and `Ratings.quantity`. Expected: accepted, since there
   is no sign constraint. Pinned in Task 3.
5. **An embedded shape with the wrong `@type`**, for example
   `unitsPreference: { '@type': 'Value', currency: 'NOK' }`. Expected:
   `zod_validation`, not a silent pass. Pinned in Task 2.
