## 1. Intent

`@flaks/onerecord` is the shared standards kernel for Cargo ERP, Skidd and
Booking Portal. 0.6.0 makes the ONE Record **Quote & Book charge chain**
(`BookingOption → Price → Ratings`, linked to `BookingRequest` and `Booking`)
parse and serialize as the IATA ontology defines it.

Two needs drive it:

1. **cargo-erp P7 needs it.** Interline partners exchange the AWB charge
   summary (weight, valuation, tax, other charges due carrier and due agent,
   prepaid or collect) over ONE Record. The ontology models these totals as
   `:Ratings` under `:Price`, reached through `BookingOption.price`. 0.5.0
   has no `Price` or `Ratings`. Without them, cargo-erp would build these
   shapes by hand, the kind of drift CLAUDE.md says this package exists to
   prevent.
2. **0.5.0 rejects standards-correct data.** Measured on 2026-11-13 against
   `dist/` of 0.5.0: a `BookingOption` that uses only ontology properties
   (`statusBookingOption`, `price`) is **rejected** (`invalid_value
   @optionStatus; unrecognized_keys statusBookingOption,price`). Only the
   package's own non-ontology shape is accepted. A standards-only peer cannot
   send us a booking option today.

## 3. Goals

- **G1. Price and Ratings.** New LogisticsObject classes with their complete
  3.2.0 property sets, full codecs (schema, serialize, serializeStrict,
  deserialize), and registration everywhere a class is registered.
- **G2. Embedded support shapes.** `Ranges` (used by `Ratings.ranges`),
  `UnitsPreference`, `CarrierProduct` and `StationRemarks` (used by
  `BookingOption` and `Booking`). Each is a shared embedded schema, like
  `Value` and `CurrencyValue`.
- **G3. Ontology properties on the three existing chain classes.**
  `BookingOption`, `BookingRequest` and `Booking` gain every ontology property
  in scope (§5.3), including the P7 links `BookingOption.price`,
  `BookingOption.statusBookingOption`, `BookingRequest.forBookingOption`,
  `BookingRequest.booking` and `Booking.bookingRequest`.
- **G4. Superset acceptance (the compatibility invariant).** For
  `BookingOption`, `BookingRequest` and `Booking`:
  (a) every payload valid under 0.5.0 deserializes under 0.6.0 to the same
  value; (b) every payload using only in-scope ontology properties
  deserializes; (c) mixes of both deserialize. Tests enforce all three.
- **G5. Ontology-conformance guard.** A committed, script-generated extract of
  the binding ontology's restrictions for the in-scope classes, plus a test
  asserting each schema's keys equal (ontology properties − documented
  deferrals) ∪ (documented legacy keys) ∪ envelope keys. Future drift fails
  CI. The same script can be pointed at the 3.3.0 file to re-prove identity.
- **G6. Correct link typing.** `FIELD_TYPES` covers the new links. The
  existing `Waybill.referredBookingOption` entry is fixed: the ontology range
  is `:Booking` (3.2.0 L2166), not `BookingOption`.

## 4. Non-goals

- **Moving the pin to 3.3.0.** The pin is package-wide
  (`CARGO_ONTOLOGY_VERSION`, ServerInformation endorsement checks, every
  class) and peers run 3.2. Because the in-scope surface is identical in
  3.3.0, 0.6.0 already serves both. A 3.3.0 migration gets its own release
  and a roadmap entry.
- **The rest of the booking area.** `BookingOptionRequest`,
  `BookingShipment`, `BookingSegment`, `BookingTimes` and
  `BookingPreferences` are v0.1-era LogisticsObject-shaped classes whose
  fields do not match the ontology. In the ontology, `BookingTimes` is
  embedded and `BookingSegment` is not a LogisticsObject. Realigning them,
  and reworking `booking-flow`, is a separate "booking Path A" release (named
  after the v0.3.0 Path A rework of Waybill and Shipment).
- **Accepting `{ "@id": … }` node references** in place of bare IRI strings,
  package-wide. That is a profile change for every class, not this release.
- **Graph-level business rules**, such as `grandTotal` = Σ `subTotal`. The
  ontology does not state them.
- **Embedded-graph (`?embedded=true`) validation changes.** Per-class
  schemas keep validating the flattened, one-object-per-IRI form.

## 5. Decisions (each is the maintainer's call)

### 5.1 Pin stays 3.2.0; cite the binding file
Rationale in §4. The spec cites 3.2.0 (`3.2-rc2`) line numbers. cargo-erp's
P7 spec cited the 3.2.1 master draft
(`cargo-erp/apps/api/src/assets/onerecord-ontology/IATA-1R-DM-Ontology.ttl`,
lines about 2 off). The content matches, but the citations need correcting
upstream (§8).

### 5.2 Price and Ratings follow the ontology exactly, including no currency
`Price` = `chargeCode`, `forBookingOption`, `grandTotal`, `ratings[]`.
`Ratings` = 13 properties (spec §3). `grandTotal`, `subTotal` and `quantity`
are `xsd:double`, so they are **plain numbers**. The ontology puts **no
currency** on `Price` or `Ratings`.

The ontology carries the offer currency in **`BookingOption.unitsPreference →
UnitsPreference.currency`** (`codes:CurrencyCode`, 3.2.0 L801). The package
models that path (G2, G3) and does not invent a currency field. This
contradicts the P7 spec, which assumed `grandTotal: CurrencyValue` and a
currency on `Ratings`. §8 lists the correction.

No sign constraint on amounts: the ontology has none, and credits or
discounts are legitimate. Consumers enforce their own business rules.

### 5.3 What each existing chain class gains, and what is deferred
Rule: add every ontology property of the class whose range is (a) a
LogisticsObject, as a bare IRI; (b) an enumeration or code list, as a token
per the package convention; (c) an XSD literal; or (d) an embedded class
modelled in G2.

Deferred: properties whose range is an embedded or non-LogisticsObject class
that the package currently models as a conflicting, legacy
LogisticsObject-shaped class. These are `bookingTimes` (on BookingOption and
Booking) and `bookingSegments` (on Booking). Adding them now would need a
second `BookingTimes` and `BookingSegment` shape beside the legacy classes.
The booking Path A release fixes the class and the property together. Until
then, a peer payload carrying them is rejected. This is documented as a
deviation and enforced by the G5 guard's deferral list.

### 5.4 Legacy (non-ontology) fields are kept, optional and deprecated
To satisfy G4 without a hard break:

| Class | Legacy key | 0.5.0 | 0.6.0 |
|---|---|---|---|
| BookingOption | `optionStatus` | required | optional, `@deprecated` (use `statusBookingOption`) |
| BookingOption | `forBookingRequest` | required | optional. It is an ontology property with no minimum cardinality, so it is not deprecated |
| BookingOption | `expiresAt` | optional | optional, `@deprecated` (use `offerValidTo`) |
| BookingOption | `preferences` | optional | optional, `@deprecated` (not an ontology property of BookingOption) |
| BookingRequest | `requestStatus`, `requestor` | required | optional, `@deprecated` |
| BookingRequest | `preferences` | optional | optional, `@deprecated` |
| Booking | `bookingStatus` | required, `REQUEST_ACCEPTED`/`REQUEST_REVOKED` | optional; values = ontology `BookingStatus` ∪ the two legacy values (legacy values `@deprecated`) |
| Booking | `forBookingRequest` | required | optional, `@deprecated` (use `bookingRequest`) |
| Booking | `forBookingOption` | optional | optional, `@deprecated` (no ontology property; the ontology links Booking → BookingRequest → BookingOption) |

Removal of deprecated keys belongs to booking Path A, with a MIGRATING entry.

### 5.5 Status enums take their ontology names
`codes` currently exports `BookingStatus` and `BookingOptionStatus` with the
non-ontology values `REQUEST_PENDING…REQUEST_REVOKED`. These duplicate
`RequestStatus` and are used nowhere in `src/` or in any consumer repo
(checked 2026-11-13 in cargo-erp and flaks-booking). 0.6.0 redefines them
with the ontology values:

- `BookingOptionStatus` = BOOKABLE, BOOKED, EXPIRED, NONBOOKABLE,
  NOT_BOOKABLE, ON_REQUEST, QUEUED. The ontology lists both NONBOOKABLE and
  NOT_BOOKABLE; both are kept verbatim.
- `BookingStatus` = CONFIRMED, DELETED, QUEUED, REJECTED.

A new `ChargeIdentifier` enum is added. This is a documented 0.x-minor break;
the migration is "use `RequestStatus`".

### 5.6 Code-list typing follows existing package precedent
Closed, small code lists become `z.enum`: `ChargeIdentifier`,
`PrepaidCollectIndicator` (`['P','C']`, as in `OtherCharge`),
`EntitlementCode` (`['C','A']`, as in `OtherCharge`), and the two status
enums.

Large or open lists become bounded strings, typed exactly like the existing
package fields of the same code list, so the same code list never has two
types:

- `otherChargeCode` like `OtherCharge.otherChargeCode`;
- `rcp` and other `CodeListElement` ranges like `WaybillLineItem.rcp`;
- `rateClassCode` like `WaybillLineItem.rateClassCode`;
- `currency` like `CurrencyValue.currencyUnit`;
- unit codes like `Value.unit`;
- `chargeCode` (25 codes) as a bounded string 1..16, like the package's
  other charge-code string fields.

Waybill numbering on BookingRequest and Booking reuses the
`Waybill.waybillPrefix` / `waybillNumber` patterns.

### 5.7 Embedded shapes copy the `Value` pattern
Strict objects with optional `'@type'` literal, no `@id`, exported schema and
type, no codec (they are not LogisticsObjects). Location:
`src/classes/shared/`, beside `value.ts`.

### 5.8 `booking-flow` stays on the legacy status model
IATA tracks the Quote & Book lifecycle with LogisticsEvents and API
ActionRequests (`distribution.md` "ONE Record mechanisms"), not with object
status fields. The `STATE_DIAGRAM` and transitions are a pre-ontology model
(deviation #11).

0.6.0 does not extend them to ontology statuses. The transition helpers keep
reading and writing the legacy fields and pass ontology fields through
unchanged. When the legacy status a helper needs is absent, for example on
an ontology-only `BookingRequest`, the helper returns
`forbidden_state_transition` with `from: '<Type>.(absent)'`. It does not
guess a state, and the locked `ParseError` kind set stays unchanged. Helpers
that build new objects keep emitting the legacy fields as today. The rework
belongs to booking Path A.

### 5.9 Link typing (`FIELD_TYPES`)
Each new LogisticsObject-ranged property whose range class the package
models gets an entry. Unmodelled ranges (`TransportLegs`, `Carrier`) are
omitted, following the existing `Waybill.billingDetails` precedent;
`Carrier` ⊂ `Company` polymorphism would also make an exact `@type` match
wrong. `Waybill.referredBookingOption` is corrected from `BookingOption` to
`Booking`, a bug fix noted in the CHANGELOG.

### 5.10 Ontology-conformance guard (G5)
A small committed script (`scripts/extract-ontology-restrictions.mjs`, no
dependencies) reads a TTL path and writes
`test/fixtures/ontology/quote-book-3.2.0.json`. The file holds, per class,
each property with its range, its cardinality (one / many), and its
declaration line, plus the source file's `owl:versionInfo` and SHA-256. The
TTL itself is not vendored.

A test then compares each in-scope schema's shape keys with the extract.
Every ontology property must be present unless it is on the documented
deferral list. Every schema key must be an ontology property, an envelope
key, or on the documented legacy list. Array-ness must match the
cardinality, and IRI-vs-embedded-vs-literal must match the range kind.

## 6. Compatibility and release

- **Version:** 0.6.0, a 0x minor. The type-level breaks are listed below.
  Runtime deserialization is a superset of 0.5.0 for the three chain classes.
- **Type-level breaks** (each gets a `MIGRATING.md` entry):
  - fields made optional, as listed in §5.4;
  - `Booking.bookingStatus` widened;
  - `codes.BookingStatus` and `codes.BookingOptionStatus` values replaced;
  - `FIELD_TYPES['Waybill.referredBookingOption']` changed;
  - `booking-flow` helpers now handle an absent legacy status.
- **Additive:** the `Price` and `Ratings` codecs; the `Ranges`,
  `UnitsPreference`, `CarrierProduct` and `StationRemarks` schemas; the
  `ChargeIdentifier` enum; and the new fields.
- **Release gates:** all `release.yml` gates must pass locally before tagging:
  `typecheck`, `lint`, `test`, `test:property`, `build`, `api:check`,
  `npm pack` inspection, and the public-exports snapshot. The baseline on
  2026-11-13: all green, 799 passed + 1 skipped, 20 property tests.
- **Publishing:** a signed `v0.6.0` tag drives `release.yml` trusted
  publishing, as in 0.5.0. Tagging, pushing and publishing need explicit owner
  approval at the end of implementation. Consumers pin `0.6.0` exactly when
  they adopt it. Skidd and Booking Portal are unaffected until they choose to
  upgrade.

## 7. Risks

| Risk | Mitigation |
|---|---|
| Superset acceptance silently drifts in future edits | G4 tests replay every existing 0.5.0 booking fixture plus a dedicated legacy corpus |
| A deprecated legacy field is mistaken for an ontology one | The G5 guard lists legacy keys explicitly; JSDoc `@deprecated` on each |
| Closed `ChargeIdentifier` enum rejects a future IATA code | The code list is identical in 3.2 and 3.3; a new code is a patch release |
| Consumers rely on the `?embedded=true` form | Out of scope (§4), unchanged behavior; noted for cargo-erp in §8 |

## 8. Consumer guidance for cargo-erp P7 (cross-repo; not package work)

Send these corrections back to the P7 spec (§3.9 "Package and ontology",
§5.6.3 table, §5.6.4):

1. Cite the binding 3.2.0 file (the NE:ONE copy, or vendor it), not the
   3.2.1 master draft.
2. `Price.grandTotal` and `Ratings.subTotal` are numbers, not `CurrencyValue`.
   The currency comes from `BookingOption.unitsPreference.currency`.
   `currency_missing` should test that path, keeping the P7-DOM-09 fallback
   for `as_agreed`.
3. Package references are bare IRI strings. cargo-erp's own Booking projector
   (`booking-to-booking.ts`) emits `{ '@id' }` objects and should switch to
   the package `Booking` type.
4. Until booking Path A ships, omit `bookingTimes` and `bookingSegments`
   from Booking objects that are validated with the package codec. The
   projector already emits `bookingStatus` CONFIRMED and DELETED, which 0.6.0
   accepts.
5. `subTotal ≥ 0` is a cargo-erp business rule, not package validation.
