## 1. Intent

`@flaks/onerecord` is the shared standards kernel used by Cargo ERP, Skidd
and Booking Portal. Release 0.6.0 makes the ONE Record **Quote & Book charge
chain** parse and serialize as the IATA ontology defines it, under the
package's wire profile (bare IRIs, bare code tokens). The chain is:

- `BookingOption → Price → Ratings`
- linked to `BookingRequest`, `Booking` and `TransportLegs`

Two needs drive this release.

1. **cargo-erp P7 needs it.** Interline partners exchange the AWB charge
   summary (WT, VC, TX, OC, OA; prepaid or collect) over ONE Record. The
   ontology models those amounts as `:Ratings` under `:Price`, reached through
   `BookingOption.price`. P7 also rebuilds routing from `TransportLegs`.
   Version 0.5.0 has none of these classes, so cargo-erp would end up
   hand-rolling them. That is exactly the drift this package exists to
   prevent.
2. **0.5.0 rejects ontology-shaped data.** Measured on 2026-11-13 against
   0.5.0 `dist/`: a `BookingOption` that uses the ontology properties
   `statusBookingOption` and `price` is rejected. Only the package's own
   non-ontology shape is accepted.

## 3. Goals

- **G1.** Add `Price`, `Ratings` and `TransportLegs` as LogisticsObject
  classes, with complete 3.2 property sets, full codecs and full
  registration.
- **G2.** Add nine embedded support shapes. Their schemas stay internal;
  their types are exported type-only.
- **G3.** Make `BookingOption`, `BookingRequest` and `Booking` **complete per
  3.2**. That means every restriction on the class itself and on
  intermediate superclasses (for Booking, `:LogisticsService`). The four
  `:LogisticsObject`-level properties are a documented package-wide gap
  (deviation #19).
- **G4. Superset acceptance.**
  - Every payload accepted by published 0.5.0 still parses, to the same
    value. This is structural equality, not semantic.
  - Ontology-only payloads parse, under the package profile.
  - Mixed payloads parse.
- **G5. Conformance guard.** IATA's MIT-licensed TTLs are vendored at a
  pinned commit, and a typed extractor feeds a test. The test checks that:
  - every schema matches the ontology;
  - legacy keys are tracked, deprecated and ratcheted;
  - each code list has a single Zod type across the package;
  - enum values match the ontology;
  - 3.2 and 3.3.0 are identical for every in-scope class.
- **G6.** `FIELD_TYPES` covers the new links. The
  `Waybill.referredBookingOption` entry is corrected from `BookingOption` to
  `Booking`.

## 4. Non-goals

- **Moving the pin to 3.3.0.** The pin is package-wide. The in-scope surface
  is identical in 3.3.0, and the guard keeps proving it.
- **Booking Path A** (target 0.7.0; legacy keys must be removed by 0.8.0):
  - realign the legacy LogisticsObject-shaped classes `BookingOptionRequest`,
    `BookingShipment`, `BookingSegment`, `BookingTimes` and
    `BookingPreferences`;
  - remove the deprecated keys;
  - replace the legacy `booking-flow`. Its roles are swapped relative to the
    ontology (deviation #21).
- **`flattenEmbeddedGraph`** for `?embedded=true` responses. It is committed
  for **0.6.1**, with its own spec.
- **`{ "@id" }` references and code-list IRIs.** These are a package-wide
  change to the wire profile.
- **Accepting timezone-less `xsd:dateTime`.** This is package-wide policy
  (deviation #22).
- **Graph-level business rules.**

## 5. Decisions (each one is the maintainer's call)

**5.1 Pin stays 3.2; cite the official IATA file.**
Line numbers are identical in the NE:ONE copy up to L10609, so the citations
hold for both files.

**5.2 Price and Ratings follow the ontology exactly.**
- `grandTotal`, `subTotal` and `quantity` are plain numbers.
- The ontology defines no currency for Price or Ratings.
  `UnitsPreference.currency` ("Preferred unit for currency") is a preference.
  It is the only currency slot on the Quote & Book path.
- The package does not invent a currency field. Using
  `BookingOption.unitsPreference.currency` for Price amounts becomes a
  **profile convention** in `ONE_RECORD_2_2_PROFILE.md`, and the package does
  not enforce it.
- Amounts carry no sign constraint.

**5.3 Completeness instead of deferral.**
In round 1, `bookingTimes` and `bookingSegments` were deferred on the grounds
that "a second shape would collide with the legacy classes". That reasoning
was wrong. Embedded schemas are internal, and the exported type names are
`EmbeddedBookingTimes` and `EmbeddedBookingSegment`. Both properties are now
included, along with the inherited LogisticsService properties.

**5.4 Legacy keys are kept, optional and deprecated** (the spec §5 [L] lists).
Deprecation is visible to consumers through hand-written exported types,
because JSDoc on Zod shape keys is lost in the emitted `.d.ts`. Every legacy
key is tracked in the guard with `removeBy: '0.8.0'`.

**5.5 Status enums take their ontology names.**
`codes.BookingStatus` and `codes.BookingOptionStatus` previously duplicated
`RequestStatus` and are used nowhere: not in `src/`, cargo-erp,
flaks-booking or cargo-handling (Skidd). They are redefined to the ontology
values. `Booking.bookingStatus` is composed from `BookingStatus.options` plus
the two legacy values.

**5.6 One type per code list.**
- A code list already typed somewhere in the package keeps that type
  everywhere.
- A new closed list becomes a named `z.enum`.
- A new open `:CodeListElement` list becomes a bounded string.

This is precedent-driven, and the guard enforces it.

**5.7 Embedded shapes follow the `Value` pattern.**
Strict objects, an optional `@type`, no `@id`, no codec, defined in
`src/classes/shared/distribution.ts`.

**5.8 `booking-flow` is legacy, contained and deprecated.**
- The helpers refuse inputs that have an ontology status
  (`ontology_status_present`).
- They refuse inputs whose legacy status is absent (`legacy_status_absent`).
- Both refusals use the existing `forbidden_state_transition` kind and its
  `reason` field.
- Every 0.5.0-valid input behaves exactly as before.

**5.9 `FIELD_TYPES`.**
- New links map to the classes the package models.
- `carrier` maps to `'*'`, because `:Carrier` ⊂ `:Company`.
- `contactPersons` maps to `'Person'`, following the Company precedent.
- `operatingTransportMeans` is left unmapped (not modelled).
- Fields inside embedded shapes are left unmapped.

**5.10 Guard.**
Vendoring the TTLs costs about 2 MB of plain text, which compresses well in
git and is not part of the tarball. In exchange, CI can reproduce the check
and verify the hashes.

## 6. Compatibility and release

**Version.** 0.6.0, a 0.x minor release. Runtime acceptance is a superset of
0.5.0 for the three chain classes.

**Type-level and behavioural breaks.** Each one gets a MIGRATING entry:
- keys that became optional;
- `Booking.bookingStatus` widened;
- `codes.BookingStatus` and `codes.BookingOptionStatus` values replaced (a
  silent runtime change for anyone parsing with them);
- `FIELD_TYPES` `referredBookingOption`;
- `booking-flow` refusals;
- three new keys in `CLASSES`, `CODECS`, the facade and the mapper.

**Reverse direction.** A 0.5.0 receiver rejects ontology-only objects. Rule:
upgrade receivers first.

**Gates.** Every `release.yml` and `ci.yml` gate must pass locally,
including `test:coverage`. Baseline on 2026-11-13: all green, 799 passed and
1 skipped, plus 20 property tests.

**Publishing.** A signed `v0.6.0` tag triggers `release.yml` trusted
publishing. Tagging, pushing and publishing need explicit owner approval.

## 7. Risks

| Risk | Mitigation |
|---|---|
| Superset acceptance drifts | The published 0.5.0 package is the oracle for a property test; existing snapshots must stay byte-identical |
| Legacy keys linger forever | A `removeBy` ratchet in the guard |
| Ontology drift between 3.2 and 3.3.0 goes unnoticed | The guard compares both vendored files |
| A closed enum rejects a future code | The code lists are identical in 3.2 and 3.3; adding a code is a patch release |
| Hand-written types diverge from the schema | A type-equality test |
