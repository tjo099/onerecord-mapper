## 1. Scope

| Item | Kind | Section |
|---|---|---|
| `Price`, `Ratings`, `TransportLegs` | new LogisticsObject classes, with codecs | §4 |
| `Ranges`, `UnitsPreference`, `CarrierProduct`, `StationRemarks`, `BookingTimes` (embedded), `BookingSegment` (embedded), `PieceGroup`, `ActivitySequence`, `ContactDetail` | new embedded shapes; no codec; type-only exports | §3 |

| `booking-flow` | explicit refusals; deprecated | §7 |
| Ontology conformance guard | vendored TTLs, extractor, test | §9 |

**Completeness rule.** For each of the six LogisticsObject classes above, the
schema MUST contain every property restricted in the class's own block or in
the block of any named superclass *strictly between* the class and
`:LogisticsObject`. For 0.6.0 that means only `:LogisticsService` for
`Booking`. The four `:LogisticsObject`-level properties (`checks`, `events`,
`externalReferences`, `skeletonIndicator`, L7690) are excluded package-wide
(deviation #19).

Out of scope:

- moving the pin to 3.3.0;
- booking Path A: realigning the legacy classes `BookingOptionRequest`,
  `BookingShipment`, `BookingSegment`, `BookingTimes` and
  `BookingPreferences`, removing legacy keys, and reworking `booking-flow`;
- accepting `{ "@id" }` references or code-list IRIs;
- graph-level business rules;
- **`flattenEmbeddedGraph`, which moves to 0.6.1** (review AR2).

## 2. Conventions

### 2.1 Package profile and field encodings

The package profile, unchanged and package-wide:

- references are bare IRI strings;
- code-list and enumeration values are bare tokens (deviation #17);
- `xsd:dateTime` values MUST carry a timezone (deviation #22, new).

Statements below about "valid" payloads mean valid under this profile.

| Ontology range kind | Zod encoding | Precedent |
|---|---|---|
| LogisticsObject class, max 1 | `safeIri().optional()` | every class |
| LogisticsObject class, many | `z.array(safeIri()).optional()` | `Waybill.waybillLineItems` |
| embedded class, max 1 / many | `<Shape>Schema.optional()` / `z.array(<Shape>Schema).optional()` | `Waybill.declaredValueForCarriage` / `.destinationCharges` |
| code list or enumeration | typed exactly like an existing package field with the same range. If there is none: a closed list becomes a named `z.enum` (§2.3); an open `:CodeListElement` subclass becomes a bounded string (§2.2) | deviation #17 |
| `xsd:double` | `z.number().optional()` (Zod 4 rejects NaN and ±Infinity; no sign constraint) | `CurrencyValue.numericalValue` |
| `xsd:integer` | `z.number().int().optional()` (Zod format `safeint`; no sign constraint) | — |
| `xsd:boolean` | `z.boolean().optional()` | `BookingPreferences.flexibleDates` |
| `xsd:dateTime` | `z.string().datetime({ offset: true }).optional()` | `MovementTime.movementTimestamp`, `BookingOption.expiresAt` |
| `xsd:duration` | `z.string().regex(XSD_DURATION).optional()`, where `XSD_DURATION = /^-?P(?=\d\|T\d)(?:\d+Y)?(?:\d+M)?(?:\d+D)?(?:T(?=\d)(?:\d+H)?(?:\d+M)?(?:\d+(?:\.\d+)?S)?)?$/` (the escaped `\|` is a plain `\|` alternation) | — |
| `xsd:string` | `z.string().min(1).max(N).optional()`, with N from §2.2, unless the same property is already typed elsewhere in the package (then identical) | `Waybill.shippingRefNo` |

Arrays: `[]` is rejected after parsing as `cardinality_violation`
(`findFirstEmptyArray`, which recurses into embedded objects). Serializers
strip empty arrays. Every object schema is `.strict()`.

| `:ContactDetailType` (open; individuals up to 23 chars, e.g. `ALTERNATE_EMAIL_ADDRESS`) | `z.string().min(1).max(64)` | — |

| `codes:ChargeIdentifier`, `codes:SpaceAllocationCode`, `codes:TransportMeansServiceType`, `:BookingStatus`, `:BookingOptionStatus` | named `z.enum` (§2.3) | — |

| free text, long (`additionalInformation`, `alternatives[]`, `shippingInfo`, `remarksText`) | `max(512)` | `Waybill.accountingInformation` |

The string bounds are editorial package policy, not ontology facets, and the
`maxStringLength` safety limit applies first. `OtherCharge` and `Waybill`
keep their inline enums: the values are identical, so there is no churn.

"One type per code list" applies only to the new fields and the precedents
named in this table; the guard's step-6 groups contain exactly those
(review round 2). Older package fields with the same range keep their
existing encodings until a dedicated alignment:

- `:CodeListElement` ranges: `Shipment.incoterms` `max(8)`, `Address.postalCode`
  `max(17)`, `CustomsInformation.country` as `safeIri`. For the new fields,
  `min(1).max(16)` is an editorial convention.
- `:textualValue`: `AccountNumber` uses `max(35)`, an FWB account-number
  limit. `ContactDetail.textualValue` follows the general
  `OtherIdentifier.textualValue` encoding, `min(1)`, because websites and
  e-mail addresses exceed 35 characters.

## 4. New LogisticsObject classes

Each class directory MUST contain `schema.ts`, `serialize.ts`,
`deserialize.ts`, `codec.ts` and `index.ts`, following the `booking-option`
pattern exactly:

- **deserialize** runs, in order: `preValidate` → context allowlist → Zod →
  lift IRI issues → empty-array check → null-prototype clone;
- **`serialize`** throws `SerializationError`. The message MUST be
  `'SerializationError[invalid_application_object]: serializeX: invalid input'`,
  following `co2-emissions/serialize.ts` and `waybill/serialize.ts`, because
  `test/unit/classes/_harness.ts` matches
  `/SerializationError|invalid_application_object/`. The booking classes'
  shorter message does not match, and those classes never used the harness
  (review round 2). The existing booking classes keep their current message;
  this release does not change it;
- **`serializeStrict`** returns a `ParseResult`;
- both serializers apply `omitEmpty`.

### 5.4 Deprecation visibility (review IM4)

JSDoc on Zod shape keys does not reach consumers through the emitted
`.d.ts`. For each of the three classes:

1. The schema keeps a `/** @deprecated … */` JSDoc on each [L] key, for maintainers.
2. The exported type is hand-written so that consumers see the deprecation. For example:

   ```ts
   type BookingOptionInferred = z.infer<typeof BookingOptionSchema>
   export type BookingOption = Omit<BookingOptionInferred, 'optionStatus' | 'expiresAt' | 'preferences'> & {
     /** @deprecated Not a ONE Record property. Use `statusBookingOption`. Removal: booking Path A (deviation #18). */
     optionStatus?: BookingOptionInferred['optionStatus']
     /** @deprecated … Use `offerValidTo`. … */ expiresAt?: BookingOptionInferred['expiresAt']
     /** @deprecated … */ preferences?: BookingOptionInferred['preferences']
   }
   ```

3. A type test MUST assert `expectTypeOf<Simplify<X>>().toEqualTypeOf<z.infer<typeof XSchema>>()`,
   where `type Simplify<T> = { [K in keyof T]: T[K] }`. A plain `toEqualTypeOf` on
   the intersection fails, and mutual assignability is too weak: because every key
   is optional, it passes even when the hand-written type drops a key (review
   round 2).
4. During implementation, a build check confirms that `dist/classes/booking-option/schema.d.ts` contains each `@deprecated` (verified once, not committed as a test).
5. Consumers see the deprecation only when they use the exported type. A value
   typed by `BookingOptionSchema.parse(x)` shows none. MIGRATING says so.

### 5.5 Superset acceptance (normative)

For each class in §5:

- **G4a, structural.** Let `S05` be the schema from the **published
  `@flaks/onerecord@0.5.0`**, installed as an npm-alias devDependency
  `onerecord-0-5-0`. For every `x` that `S05` accepts, `S06` also accepts `x`,
  and `S06.parse(x)` deep-equals `S05.parse(x)`. This says nothing about
  semantics: legacy booking-flow writes `forBookingRequest` with
  quote-request meaning (deviation #21).
- **G4b.** An input that uses only the envelope and [O] keys, with
  profile-valid values, parses.
- **G4c.** An input that mixes [O] and [L] keys parses.
- **G4d.** An input that carries a `:LogisticsObject`-level property
  (`skeletonIndicator`, `events`, `checks`, `externalReferences`) fails with
  `unrecognized_keys`, per deviation #19.

**Reverse direction.** A 0.5.0 receiver rejects ontology-only objects from a
0.6.0 producer, because of its required legacy keys and `.strict()`.
MIGRATING MUST say "upgrade receivers before producers emit ontology-only
booking objects".

  whitespace (RFC 3987 IRIs cannot), so the regex becomes
  `/^[a-zA-Z][a-zA-Z0-9+.\-]*:\S*$/`.
- This is a public function, and the change makes it stricter.
- CHANGELOG lists it under "Fixed", and deviation #9 records the remaining
  limitation: a whitespace-free string in a non-IRI field is still checked
  for canonical form.

## 7. `booking-flow` (`src/booking-flow/`)

The legacy model's roles are swapped relative to the ontology (deviation
#21). The legacy model treats `BookingRequest` as a quote request and
`BookingOptionRequest` as a booking request. 0.6.0 contains it as follows:

- **All five helpers** (`acceptBookingRequest`, `acceptBookingOption`,
  `rejectBookingOption`, `revokeBookingOption`,
  `acceptBookingOptionViaRequest`), plus `STATE_DIAGRAM` and `canTransition`,
  get `@deprecated` JSDoc pointing to booking Path A. That JSDoc sits on
  exported declarations, so it is emitted.
- **Ontology status present.** If a BookingOption input carries
  `statusBookingOption`, the helper returns `{ kind:
  'forbidden_state_transition', from: 'BookingOption.' +
  opt.statusBookingOption, to: <action>, reason: 'ontology_status_present',
  path: '$' }`. This check runs first.
- **Legacy status absent.** If the legacy status the helper's model needs is
  missing, the helper returns `{ kind: 'forbidden_state_transition', from:
  '<Type>.(absent)', to: <action>, reason: 'legacy_status_absent', path: '$'
  }`. The missing status is `requestStatus` for `acceptBookingRequest` and
  `optionStatus` for the four BookingOption helpers.
- **No 0.5.0-valid input changes behaviour.** In 0.5.0, `optionStatus` and
  `requestStatus` were required, and `statusBookingOption` was rejected by
  the schema.
- **`acceptBookingOption`** includes `forBookingRequest` in the Booking it
  returns only when the input has one. This is runtime hygiene: Zod 4 infers
  `key?: T | undefined`, so the type would allow it either way. The output
  must still validate against `BookingSchema`.
- **No ParseError kind is added**, so `parse-error-kinds-locked` is unchanged.
- Update the comment at the top of the file and deviation #11.

### 9.2 Extractor: `test/util/ontology-extract.ts`

Written in TypeScript, so it is typechecked and linted. It has no
dependencies. It MUST:

- split lines on `/\r?\n/`;
- identify class blocks, anchored at column 0, by **either** of two patterns:
  - DM file: `^:(\w+) rdf:type owl:Class\b`;
  - CL file: `^<https://onerecord.iata.org/ns/code-lists/(\w+)> rdf:type owl:Class\b`;
- end a block at the first line that ends with ` .` at bracket depth 0,
  counting `[`/`]` outside string literals;
- read named superclasses (`rdfs:subClassOf :X`) at depth 0 only;
- treat a bracket as a restriction **only** when it opens with
  `[ rdf:type owl:Restriction`. Inside a restriction, recognise
  `owl:onProperty`, `owl:allValuesFrom` and `owl:maxCardinality`, and **throw
  on any other restriction predicate**. The throw applies only to the
  requested classes and their intermediate superclasses. It cannot apply to
  every class, because 3.3.0's `:LogisticsEvent` legitimately carries an
  `owl:minCardinality` (erratum after plan review). Other brackets, such as
  `owl:equivalentClass [ rdf:type owl:Class ; owl:oneOf ( … ) ]` on
  `:BookingStatus` (L5729) and `:BookingOptionStatus` (L5490), are not
  restrictions;
- read `owl:oneOf ( … )` lists, which may be nested inside
  `owl:equivalentClass`. A value is the local name of `:X`, or the `#fragment`
  of `<…/code-lists/Name#X>`;
- record each property's declaration line.

Kind classification. Test in this order; the first match wins:

1. `xsd:*` → `literal`.
2. `code`, for any of: a `codes:*` range; `:CodeListElement`; a class that
   has an `owl:oneOf`; a class whose transitive named superclass chain
   reaches `:CodeListElement`. This test runs **before** `iri`.
3. `iri`: the transitive named superclass chain reaches `:LogisticsObject`.
4. Anything else → `embedded`.

Its API:

- `extractClasses(text, names, { inherit: 'intermediate' })` returns, per
  class, its line, superclasses and properties. Each property carries
  `{ range, kind, many, declLine, from }`.
- `kind` is classified as described above.
- `inherit: 'intermediate'` merges in properties from superclasses up to,
  but not including, `:LogisticsObject`.
- `extractOneOf(text, iriOrName)` returns the values of an enumeration or
  code list, from the DM or CL file.
- `sha256Lf(text)` returns the SHA-256 of the LF-normalised text.

## 13. Consumer guidance for cargo-erp P7 (cross-repo note; not package work)

1. Cite the official 3.2 file at commit `49e8ac1`, not the 3.2.1 master draft.
2. Currency:
   - `Price.grandTotal` and `Ratings.subTotal` are numbers, not `CurrencyValue`.
   - The ontology has no currency for them; `UnitsPreference.currency` is a
     preference.
   - Set `BookingOption.unitsPreference.currency`, as the profile convention
     recommends.
   - Receivers fall back to the Waybill's `CurrencyValue` units
     (`WaybillLineItem.rateCharge.currencyUnit`, `taxAmount`,
     `OtherCharge.otherChargeAmount`), then to P7-DOM-09.
3. References are bare IRI strings, and code values are bare tokens.
   - Switch `booking-to-booking.ts` and `product-type-to-carrier-product.ts`
     away from `{ '@id' }` objects to the package types.
   - Never emit empty arrays: `bookingSegments: []` is rejected.
4. Emit ontology keys only: `statusBookingOption`, `bookingRequest` and so
   on. Do not emit the deprecated `requestStatus`, `requestor`,
   `optionStatus`, `forBookingRequest`-on-Booking, or `forBookingOption`-on-Booking.
5. `?embedded=true` responses must be split into per-node objects before
   per-class validation. Until 0.6.1's `flattenEmbeddedGraph`, use a local
   splitter driven by `FIELD_TYPES`.
   - Under `dispatchGraphWalk` or `createMapper({ graphWalk: true })`, every
     embedded node that contains nested objects MUST carry `@type`. This
     applies, for example, to `bookingSegments[i]` and `pieceGroups[i]`.
6. `subTotal ≥ 0` is a cargo-erp business rule.
7. BookingShipment is still the legacy shape (Path A). An ontology-shaped
   BookingShipment from the projector (`booking-to-booking-shipment.ts`) is
   rejected by the 0.6.0 codec, so do not validate it with the package codec
   yet.
